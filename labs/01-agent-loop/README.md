# Lab 01 — 最小 agent loop

## 这个 lab 想让你看见什么

**agent 不是魔法，是一个 while 循环。** 剥掉所有框架、SDK、工具协议之后，骨架只有四步：

```
用户任务 → 模型决策 ──有工具调用──→ 执行工具 → 观察到结果 ──┐
              ↑                                            │
              └────────────────────────────────────────────┘
              │
              └──产出最终答案──→ 结束
```


不需要 API key，不需要联网。**唯一被伪造的是"模型"**：`FakeModel.decide()` 用几条 if 规则假装在思考。
循环、工具协议、消息历史、错误回传、终止条件全是真的。

## 逐行观察点

跑之前先猜，跑完对照：

1. **第 1 步**：模型决定调 `calculator("12*(3+4)")`。它凭什么"知道"有这个工具？→ 靠 `TOOL_SCHEMAS` 里的 description。
2. **第 2 步**：`84/0` 抛 `ZeroDivisionError`。**注意循环没有崩** —— `execute_tool()` 把异常包成字符串 `ERROR: ...` 塞回历史。这是 agent 能自我纠错的原因：错误对模型来说只是又一条观察结果。
3. **第 3 步**：模型看到错误后没有重试除零，而是换了个工具继续。**决策是基于完整历史做的，不是基于最后一条消息。**
4. **第 4 步**：模型输出 `final`，循环退出。终止有两个出口：模型给答案，或者撞到 `max_steps`。

## 三个动手练习（按难度排）

1. **加工具**：加一个 `list_dir(path)`，在 `TOOLS` 和 `TOOL_SCHEMAS` 里各注册一次，然后改任务让它必须用到。体会"注册 + 描述"这两件事缺一不可。
2. **拆保护**：把 `max_steps` 改成 3 再跑。你会看到死循环保护触发。**想一想：如果一个任务的正确答案需要 5 步，而你的上限是 3 步，用户看到的是什么？**
3. **接真模型**：把 `FakeModel.decide()` 换成真实 LLM 调用。这是从"玩具"到"agent"的唯一一步，而且**只有这一步**。你会发现难点不在循环，而在于：怎么把工具 schema 转成该模型要的格式、怎么解析它返回的 tool_call、怎么处理它调用不存在的工具。
