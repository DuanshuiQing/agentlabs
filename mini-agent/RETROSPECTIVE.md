## 4. 五个关键设计决定

### 4.1 `ToolSpec`：schema 与校验只能有一个数据源（第 3 步）

模型的参数依据（发给它的 JSON Schema）和我们自己的校验规则，描述的是同一份东西。
手工维护两份 → **模型老实按 schema 填参数，却被我们的校验判为非法**——模型没错，代码错了。

```python
_TOOL_SPECS   # 唯一手写的地方
_REGISTRY     = {spec.name: spec for spec in _TOOL_SPECS}   # 派生
TOOLS         = [spec.schema()  for spec in _TOOL_SPECS]    # 派生
```

**兑现验证**：第 8 步加 `list_dir` 时，只改了 **2 处**（函数 + `_TOOL_SPECS` 一条）。
`_REGISTRY` / `TOOLS` / `dispatch` / 超时 / 错误翻译 / 轨迹落盘**一行未动**。

### 4.2 `dispatch` 是唯一允许失败汇聚的边界（第 3、5 步）

```
1. 查表   → unknown_tool
2. 校验   → bad_arguments
3. 执行   → tool_raised / tool_timeout
4. 保证返回 str → bad_return_type
```

`dispatch` 里**从头到尾没出现过任何具体工具名**。因为 `run()` 里那三行调用工具
**一行错误处理都没有**——不确定性全被挡在这个边界之外。

### 4.3 错误文本是**白名单翻译**，不是正则清洗（第 5 步）

原来那句 `ERROR: {异常类名}: {原始报错}` 的真实形态：

```
ERROR: FileNotFoundError: [Errno 2] No such file or directory: 'D:\\Agent_test\\mini-agent\\data\\nope.txt'
```

107 字符里有主机绝对路径、有 repr 转义出来的双反斜杠。改成：

```
ERROR: 文件不存在：data/nope.txt（本项目路径都相对 mini-agent 目录写，不带盘符）
```

56 字符。**改法不是"用正则把路径洗掉"——黑名单永远漏；改法是只输出我们自己拼的文本，
认不出的异常一律丢弃原始信息。**

> ⚠️ **这一条的成本收益尚未实测。** 字符数省 52%，但**不能由字符数外推 token 数**
> （中文单字比 ASCII 单字符贵得多）。第 7 步之后 `usage` 已落盘，
> 这条可以且应该实测——但它还没做。

### 4.4 `Observation(str)`：接口的承诺保持窄，信息搭在车顶上（第 7 步）

要求冲突：`dispatch` 必须**一定返回字符串**，但复盘需要知道**为什么**失败。
解法是 `str` 的子类：

```
模型看到的   —— 就是这段字符串，一个字符都没变
复盘代码看到 —— 还能读到 error_kind / error_type
isinstance(x, str) 依然为真
```

同一个原则在项目里出现了三次：

| 步 | 两个受众 | 一个通道 | 解法 |
| --- | --- | --- | --- |
| 5 | 模型 / 复盘者 | `dispatch` 的返回值 | 文本里只留人话，类名搭车顶 |
| 6 | 用户 / 程序 | `run()` 的返回值 | `Result.answer` vs `Result.ok` |
| 7 | 模型 / 复盘者 | 观察文本 | `Observation(str)` |

### 4.5 安全边界放在路径解析这一个入口（第 9 步）

设计写工具时回头查读侧，发现 `read_file(".env")` **一直能读到密钥**
（实测 929 字符，含真 key），而它会作为观察文本**发回远端服务商**。
`list_dir` 隐藏了点文件，`read_file` 却没有查。

修法不是给 `read_file` 打补丁，而是把黑名单放进 `_resolve()`：
`read_file` / `list_dir` / `append_file` 一并受保护，将来加第 5 个工具也不用有人记得补。

**和 4.1 是同一种思路：安全边界也只能有一个入口。**

## 7. §4.5 四问的答案

> **1. 为什么工具的错误要转成文本回喂，而不是直接 `raise`？**

因为**只有模型能根据错误信息改变策略**。而关键在于：

- **异常是控制流，观察文本是数据流。** 抛异常是从调用栈跳出去；回喂是往 `messages` 里加一条。
- **我们的循环只会读数据流。** 整个 loop 就是"往 `messages` 里 append，然后再发一次请求"。
- 模型是**无状态**的：它发完 `tool_calls` 这一轮就结束了，它不可能知道调用失败。
  所以"中断"的对象**不是模型，是我们自己的循环**——一个本可"换个路径再试一次"的任务
  变成了一次 crash。

> **2. agent 与 workflow 的区别是什么？谁更可控、谁更通用？**

**唯一的分界线是"谁决定下一步"**：workflow 里它写在代码里，agent 里它由模型每轮生成。
其余差异都是推论。

- workflow **更可控**（你说了算）——但**不要说它"更可靠"**。
  它只在被设计覆盖的输入分布内可靠；超出之后它要么失败，要么**静默地给出错误结果**，
  而且不会告诉你"这个输入我没设计过"。
- agent **更通用**——它在分布外可能自己绕过去（T3 就是：文件不存在，它如实报告而不是编造），
  也可能**烧钱乱走**（T4 原题面：47288 tokens 全部打了水漂）。

> **3. 为什么工具描述的质量，常常比 system prompt 更影响成功率？**

因为 `description` 是**模型选不选这个工具、怎么填参数的唯一依据**——它看不到你的 Python 代码。

1. **离决策点更近**：system prompt 在任务开始前给通用规范；description 就在模型
   正要决定"调哪个、填什么"的那一刻眼前。
2. **精度不同**：system prompt 只能写模糊的（"你要仔细"）；description 能写可执行的
   （"path 必须相对 mini-agent 目录，例如 `data`"）。
3. **它是接口文档 + 提示词的合体**：schema 管"参数长什么样"，description 管
   "什么时候该用它"，后者只能靠自然语言表达——而自然语言就是提示词。

> **一个反证**：整个阶段 0 **没有写过一行 system prompt**，成功率依然不低。

> **4. `dispatch` 一律返回字符串、绝不抛异常——为什么这是整个设计的关键？**

因为它是**全项目唯一的失败汇聚点**。它若允许抛异常，上面四层全塌：

| 塌掉的 | 为什么 |
| --- | --- |
| 循环 | 可恢复的失败变成 crash |
| `Observation` | 结构化字段**挂在返回值上**，抛异常就没有返回值 |
| 错误翻译 | 白名单翻译发生在 `except` 里；异常穿出去就没人翻译，而**原始异常带着主机绝对路径** |
| JSONL 轨迹 | 那一步在轨迹里直接消失，复盘时看不出"它试过但失败了" |
| 超时语义 | `ToolTimeout` 是抛给我们自己看的信号，必须被 `dispatch` 吃掉 |

**边界很重要**：`run()` 自己是**可以**抛的（`max_steps < 1` 那个 `ValueError`）。
这条规矩不是"全项目不许抛异常"，而是"**在工具执行边界上不许抛；边界之外随便抛**"。

## 12. 第 10 步补记：补齐 `calculator` + T5（2026-10-13）

### 12.1 做了什么

按 PLAN §4.3 的硬要求（"用 `ast` 白名单，**绝不用 `eval()`**"）补上第 4 个工具。
它的风险面和另外三个**完全不同**：

| | 危险是什么 | 靠什么挡 |
| --- | --- | --- |
| `read_file` / `list_dir` / `append_file` | 碰到不该碰的路径 | `_resolve` 的两道拒绝 |
| **`calculator`** | **不碰任何路径，但能被算爆** | 它自己的一整套闸门 |

**三道闸，按代价从低到高：**

1. 表达式长度上限 200 字符（**解析前**就挡，最便宜）
2. **节点类型白名单**：`ast.walk` 走一遍，**先拒绝，再求值**
3. 每一步结果的绝对值上限 `1e15` + 指数上限 1000（挡 `9**9**9` 这类算爆的）

白名单用**精确类型**匹配（`type(node) not in _ALLOWED_NODES`），**不用 `isinstance`** ——
`isinstance` 会把子类放进来，而 ast 的继承关系不是为安全设计的。

### 12.2 本地验证：27 条输出 + 6 条正确性断言

新增 11 条 calculator 失败用例，几条值得单列：

| 表达式 | 结果 |
| --- | --- |
| `__import__('os').system('dir')` | `表达式里不允许出现 Call` ← **白名单存在的理由** |
| `(1).__class__` | `不允许出现 Attribute` |
| `x + 1` | `不允许出现 Name` |
| `'abc'` | `结果不是实数（str）` |
| `True` | `结果不是实数（bool）` ← bool 是 int 的子类，必须**单独**挡 |
| `9**9**9` | `指数 387420489 超过上限 1000` |
| `(-1)**0.5` | `结果不是实数（complex）` |
| `1/0` | `除数为零`（走的是**异常翻译**路径，不是白名单） |

自检规模从 16 条输出涨到 **27 条**；两条泄露断言（主机路径 / 密钥）仍全过。

### 12.3 T5：一次运行同时回答了两个问题

为 `calculator` 加了一条真实任务 **T5**（PLAN §4.4 的四条之外，属第 10 步新增，见 PLAN §6 偏差）：

> `读取 data/budget-Q4.txt，把这笔预算按 7:5:3 分成三份，告诉我每份多少元（保留两位小数）。`

**题面刻意不提 `calculator`。** 结果（`run-20261013-212734`，`ok=True / steps=3 / 3253 tokens`）：

```
[第 1 轮] read_file('data/budget-Q4.txt')
[第 2 轮] calculator × 3  ← 一轮里并行三个
          3800 * 7 / 15 = 1773.33
          3800 * 5 / 15 = 1266.67
          3800 * 3 / 15 = 760
[第 3 轮] stop —— 表格作答，合计 3800.00
```

**它主动用了这个工具，尽管没人告诉它有这个工具。** 这直接回答 PLAN §4.5 Q3：
**description 的质量决定模型选不选它** —— 这次它选对了。

这个数据点是白捡的：本来 Q3 要单做一个消融实验，现在至少有了"正向"的一半。
**反向那一半仍未做**：把 description 改含糊，看触发率是否下降（阶段 1 的任务）。

### 12.4 顺带一个发现：答案对，附带解释里有一处错

模型自己补了一句：

> （7/15 和 5/15 实际是 1773.333… 和 1266.666…，四舍五入到两位小数后**两份各多算了** 0.003…，凑巧正负相抵）

**数字全对**（1773.33 + 1266.67 + 760 = 3800.00），但**"两份各多算了"这个说法是错的**：
1773.333… → 1773.33 是**往下舍**，只有 1266.666… → 1266.67 才是往上入。
一进一出，所以才是"正负相抵"。

**这又是一次 §6 的例证**：判定只能落在**数字**上（性质断言），
不要试图断言模型的**解释文字** —— 它会给出正确的数字，配上一句不精确的说明。
这也是为什么阶段 1 的 expected 必须写成
`assert "1773.33" in answer and "1266.67" in answer and "760" in answer`，
而**不是**去匹配那句解释。

## 13. 阶段 1 补记：T3 的判据是错的（2026-10-28）

> 这一节**修正本文 §§2–3 的一条判据**，原文保留不删 —— 负结果要照实留档。
> 口径裁定见 [PLAN §2 第 9 条](../PLAN.md)。

### 13.1 发现了什么

阶段 1 第 2 步跑了基线 **5 轮 × 5 条 = 25 次**，**T3 五跑全败**（0/5）。
查轨迹发现 5 次的动作序列**一模一样**：

```
read_file("data/handbook-v2.txt")   ← 失败：文件确实不存在
list_dir("data")                     ← 看到有 handbook.txt
read_file("data/handbook.txt")       ← 读了"名字最接近"的那份
→ 答案里明确写 v2 不存在，然后总结的是**另一个真实存在的文件**，并标了出处
```

而本文 §2 那条判据是：「答案里不许出现 `handbook.txt` 的正文串」。
它把「**编造 v2 的内容**」（`expect` 要防的）和「**标注出处的真实文件摘要**」
（模型做的）混成了一件事。

还有一次是纯技术性误杀：那次模型**用英文回答**（`that file doesn't exist`），
而判据查的是中文 `"不存在"`。

### 13.2 重新归类：阶段 0 那四次运行其实是三种行为

本文 §2 的表格把四次运行归成「2 干净 / 2 有偏差」。现在有了第 3、4 种样本，
应当分成**三类**：

| 行为 | 该不该算失败 | 样本 |
| --- | --- | --- |
| 编造一个**不存在的路径**去试（`data/handbook-v1.txt`） | **失败** | 第 2 次（无轨迹） |
| 被错误提示里的示例路径带偏，去读了 `handbook.txt` | **失败** | 第 1 次（无轨迹） |
| 如实说 v2 不存在，**另外**总结一个真文件并标出处 | 不是本文要测的失败 | 基线 5 次 |

第 1 次归因也标错了：它不是"模型行为"，是**实验设计**问题 ——
我自己的错误提示里写了「例如 `data/handbook.txt`」（本文 §5 第 1 条已记）。

### 13.3 判据改成什么

1. **多语言**查"如实说失败"（`不存在` / `not found` / `doesn't exist` / `did not find` …）
2. 出现 `handbook.txt` 正文串时，答案里必须**同时**出现 `handbook.txt`（=标了出处，不是冒充）
3. 答案必须提到本题对象 `handbook-v2`（否则"判的大概不是这道题的答案"）

离线重判全部 **7 份** T3 轨迹（阶段 0 的 2 份 + 基线的 5 份）：
**旧判据 2/7，新判据 7/7**，零 API 成本。

### 13.4 这次修改的代价，照实记

**T3 不再是零重叠断言。** 本文 §5 第 25 条曾写"T3 是特异性矩阵里唯一零重叠的一条"，
去掉那条反例排除之后，T3 的答案开始**同时通过 T1 和 T4 的断言** ——
因为被接受的摘要必然引用 handbook 正文，而正文里就有 `run-<时间戳>.jsonl`，
那正是 T1 的答案。

**这个代价补不掉**：只要允许"引用并标出处"，答案里就会带上别的任务的答案。
它意味着矩阵里的重叠从 3 处变成 5 处。记在 PLAN §5 第 25 条，作为
"子串断言对『不编造』这类语用性质只能做近似"的实证。

### 13.5 一条方法论

**断言可以事后重跑，运行不能。** 发现判据错的时候，25 次运行已经花掉
**90053 tokens**。如果选择"改题面重跑"，那就是为**自己的判据 bug** 再付一次 90053。

正解是：原始结果 `real-*.json` **永不覆盖**，改完断言用同一批轨迹重判，
另存 `rejudged-*.json`，两份并排。实测 25 条里恰好 **5 条翻转，全是 T3，其余 20 条一条没动** ——
这个"只有该动的动了"本身就是"改动没有副作用"的证据。
