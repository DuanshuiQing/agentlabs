## 4. 五个关键设计决定

### 4.1 `ToolSpec`：schema 与校验只能有一个数据源（第 3 步）

模型的参数依据（发给它的 JSON Schema）和我们自己的校验规则，描述的是同一份东西。
手工维护两份 → **模型老实按 schema 填参数，却被我们的校验判为非法**——模型没错，代码错了。

```python
_TOOL_SPECS   # 唯一手写的地方
_REGISTRY     = {spec.name: spec for spec in _TOOL_SPECS}   # 派生
TOOLS         = [spec.schema()  for spec in _TOOL_SPECS]    # 派生
```

**兑现验证**：第 8 步加 `list_dir` 时，只改了 **2 处**（函数 + `_TOOL_SPECS` 一条）。
`_REGISTRY` / `TOOLS` / `dispatch` / 超时 / 错误翻译 / 轨迹落盘**一行未动**。

### 4.2 `dispatch` 是唯一允许失败汇聚的边界（第 3、5 步）

```
1. 查表   → unknown_tool
2. 校验   → bad_arguments
3. 执行   → tool_raised / tool_timeout
4. 保证返回 str → bad_return_type
```

`dispatch` 里**从头到尾没出现过任何具体工具名**。因为 `run()` 里那三行调用工具
**一行错误处理都没有**——不确定性全被挡在这个边界之外。

### 4.3 错误文本是**白名单翻译**，不是正则清洗（第 5 步）

原来那句 `ERROR: {异常类名}: {原始报错}` 的真实形态：

```
ERROR: FileNotFoundError: [Errno 2] No such file or directory: 'D:\\Agent_test\\mini-agent\\data\\nope.txt'
```

107 字符里有主机绝对路径、有 repr 转义出来的双反斜杠。改成：

```
ERROR: 文件不存在：data/nope.txt（本项目路径都相对 mini-agent 目录写，不带盘符）
```

56 字符。**改法不是"用正则把路径洗掉"——黑名单永远漏；改法是只输出我们自己拼的文本，
认不出的异常一律丢弃原始信息。**

> ⚠️ **这一条的成本收益尚未实测。** 字符数省 52%，但**不能由字符数外推 token 数**
> （中文单字比 ASCII 单字符贵得多）。第 7 步之后 `usage` 已落盘，
> 这条可以且应该实测——但它还没做。

### 4.4 `Observation(str)`：接口的承诺保持窄，信息搭在车顶上（第 7 步）

要求冲突：`dispatch` 必须**一定返回字符串**，但复盘需要知道**为什么**失败。
解法是 `str` 的子类：

```
模型看到的   —— 就是这段字符串，一个字符都没变
复盘代码看到 —— 还能读到 error_kind / error_type
isinstance(x, str) 依然为真
```

同一个原则在项目里出现了三次：

| 步 | 两个受众 | 一个通道 | 解法 |
| --- | --- | --- | --- |
| 5 | 模型 / 复盘者 | `dispatch` 的返回值 | 文本里只留人话，类名搭车顶 |
| 6 | 用户 / 程序 | `run()` 的返回值 | `Result.answer` vs `Result.ok` |
| 7 | 模型 / 复盘者 | 观察文本 | `Observation(str)` |

### 4.5 安全边界放在路径解析这一个入口（第 9 步）

设计写工具时回头查读侧，发现 `read_file(".env")` **一直能读到密钥**
（实测 929 字符，含真 key），而它会作为观察文本**发回远端服务商**。
`list_dir` 隐藏了点文件，`read_file` 却没有查。

修法不是给 `read_file` 打补丁，而是把黑名单放进 `_resolve()`：
`read_file` / `list_dir` / `append_file` 一并受保护，将来加第 5 个工具也不用有人记得补。

**和 4.1 是同一种思路：安全边界也只能有一个入口。**

## 7. §4.5 四问的答案

> **1. 为什么工具的错误要转成文本回喂，而不是直接 `raise`？**

因为**只有模型能根据错误信息改变策略**。而关键在于：

- **异常是控制流，观察文本是数据流。** 抛异常是从调用栈跳出去；回喂是往 `messages` 里加一条。
- **我们的循环只会读数据流。** 整个 loop 就是"往 `messages` 里 append，然后再发一次请求"。
- 模型是**无状态**的：它发完 `tool_calls` 这一轮就结束了，它不可能知道调用失败。
  所以"中断"的对象**不是模型，是我们自己的循环**——一个本可"换个路径再试一次"的任务
  变成了一次 crash。

> **2. agent 与 workflow 的区别是什么？谁更可控、谁更通用？**

**唯一的分界线是"谁决定下一步"**：workflow 里它写在代码里，agent 里它由模型每轮生成。
其余差异都是推论。

- workflow **更可控**（你说了算）——但**不要说它"更可靠"**。
  它只在被设计覆盖的输入分布内可靠；超出之后它要么失败，要么**静默地给出错误结果**，
  而且不会告诉你"这个输入我没设计过"。
- agent **更通用**——它在分布外可能自己绕过去（T3 就是：文件不存在，它如实报告而不是编造），
  也可能**烧钱乱走**（T4 原题面：47288 tokens 全部打了水漂）。

> **3. 为什么工具描述的质量，常常比 system prompt 更影响成功率？**

因为 `description` 是**模型选不选这个工具、怎么填参数的唯一依据**——它看不到你的 Python 代码。

1. **离决策点更近**：system prompt 在任务开始前给通用规范；description 就在模型
   正要决定"调哪个、填什么"的那一刻眼前。
2. **精度不同**：system prompt 只能写模糊的（"你要仔细"）；description 能写可执行的
   （"path 必须相对 mini-agent 目录，例如 `data`"）。
3. **它是接口文档 + 提示词的合体**：schema 管"参数长什么样"，description 管
   "什么时候该用它"，后者只能靠自然语言表达——而自然语言就是提示词。

> **一个反证**：整个阶段 0 **没有写过一行 system prompt**，成功率依然不低。

> **4. `dispatch` 一律返回字符串、绝不抛异常——为什么这是整个设计的关键？**

因为它是**全项目唯一的失败汇聚点**。它若允许抛异常，上面四层全塌：

| 塌掉的 | 为什么 |
| --- | --- |
| 循环 | 可恢复的失败变成 crash |
| `Observation` | 结构化字段**挂在返回值上**，抛异常就没有返回值 |
| 错误翻译 | 白名单翻译发生在 `except` 里；异常穿出去就没人翻译，而**原始异常带着主机绝对路径** |
| JSONL 轨迹 | 那一步在轨迹里直接消失，复盘时看不出"它试过但失败了" |
| 超时语义 | `ToolTimeout` 是抛给我们自己看的信号，必须被 `dispatch` 吃掉 |

**边界很重要**：`run()` 自己是**可以**抛的（`max_steps < 1` 那个 `ValueError`）。
这条规矩不是"全项目不许抛异常"，而是"**在工具执行边界上不许抛；边界之外随便抛**"。

**与计划的偏差**：[PLAN.md](../PLAN.md) §4 写的是"唯一产出物：`mini-agent/`，约 300 行 Python"。
实测本体 **1257 行（代码 691 行）**，约是估计值的 2–4 倍。
多出来的部分主要是 **docstring + 自检代码**（注释与文档字符串占 24%）。

**这个偏差值得保留，不值得削平**：自检代码（`tools.py` 的失败路径断言、
`check_data.py` 的 fixture 断言）不是"额外的负担"，而是**把口头规格变成可执行物**的唯一办法——
本文 §5 的 10 条负结果里，有 3 条是这些断言直接抓出来的。

**口径说明（这张表怎么算的）**："代码" = 总行 − 空行 − 纯注释行 − docstring 行。
不同的计数法会得到不同数字，**报数时必须连口径一起报**。另一个口径供对照：
用 `ast` 统计"唯一语句起始行"（多行语句只算 1 行），agent 本体是 **600 行**、六个文件合计 **819 行**。
两种口径下"实际是计划的 2–4 倍"这个结论都成立。
