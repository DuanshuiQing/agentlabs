# 怎么写一个合格的 skill（以论文精读为例）

> 对应 PLAN §4 阶段 2。跑分例是 [`../.dsh/skills/explaining-papers/`](../../.dsh/skills/explaining-papers/)。
> 结构本身（三层披露、发现规则）见同目录的 skill 结构说明；这一页只讲**动手顺序**。

## 0. 先定义"合格"：四条可检验的证据

一个 skill 合格，是指这四件事都能拿出来：

| 证据 | 怎么证明 |
|---|---|
| ① 能被发现 | catalog 里出现它，名字与目录一致 |
| ② 能被触发 | **新上下文里只描述任务、不提名字**，它也会被加载 |
| ③ 加载后做对 | 产出物、格式、判据都对 —— 由校验器证明，不是由"看起来挺好" |
| ④ 做错时能报错 | 校验器有 **`--self-test`**，能证明它真的会报 |

> 最坏的 skill 不是"触发不了"，是**能触发、每次做出来的东西都不一样，而没人发现**。
> ③④ 就是防这个的。

下面八步，按这个顺序做，不要跳。

---

## 第 1 步：先找"事实标准"，不要先写 SKILL.md

**要决定什么**：这个 skill 固化的到底是哪套做法。

我做的第一件事不是写文件，是读 `notes/papers/` 里**已经存在的 4 篇笔记 + INDEX**，把"每次都出现的东西"抄出来：

- 节号顺序固定（五段速记 → 一句话结论 → … → 术语表）
- 关键数字一律带 `[p.N]` 页码锚点（实测每篇 39–96 个）
- 顶部元信息表（作者 / 出处 / 原文 / **阅读范围**）
- INDEX 的 L0 卡固定 6 行、矩阵固定 9 维
- 有一节叫「已知缺陷与未核实清单」，而且里面写了自己猜错过什么

**为什么不能凭空设计**：skill 是**把已经做对过的流程固化下来**。凭空设计一套格式，它必然和你实际产出的东西不一致 —— 于是你有了两个标准，而且不知道哪个对。

**判据**：能列出 ≥5 条"我这几篇里每次都出现的东西"吗？列不出，说明流程还不稳定，**先手工做一遍再写 skill**。

---

## 第 2 步：写 `description`（层 1）—— 全篇最难的一段

**要决定什么**：什么情况下该想起这个 skill。它只有一次机会 —— 不加载就没有后面所有层。

我写的是三段式：

```
[做什么] 把一篇论文读成"能讲、能反驳、能落到代码"的笔记：
         产出 L1 笔记（固定 10 节）、更新 INDEX（L0 卡 + 矩阵 + 三种读法 + 落地清单），
         按需再出自测题和组会发言稿。
[何时用] 当用户说"帮我把这篇论文搞明白 / 整理一下这篇 paper / 准备组会讲这篇 /
         这篇对我的项目有什么用"时使用。
[负向指令] 不要直接开始写摘要 —— 先跑一次页码抽取，再按节填。
```

| 写法 | 反例 | 为什么不行 |
|---|---|---|
| 做什么 | "这个 skill 是关于论文阅读的" | 只说了主题，没说产出 ← 模型无法判断"该不该用" |
| 何时用 | "用于学术场景" | 太泛，等于没说；要用**用户真的会说的那句话** |
| 负向指令 | （不写） | 模型会直接开始写摘要 —— 这是最容易发生的失败 |

**判据**：让一个没看过你项目的人读这段，他能不能判断"我现在该不该用它"。
我这版把"不要直接开始写摘要"写进去了，因为**那正是最容易发生的错误起步动作**。

---

## 第 3 步：写正文 `SKILL.md`（层 2）—— 只放"每次都要执行的骨架"

**要决定什么**：哪些东西是"每次打开都要看一遍的"。

我的正文 56 行，只有四块：

1. **产出物分档**（一份必做 / 一份每批必更 / 两份按需）—— 一句话说清"几份文件"
2. **顺序**（六步，且写明"不能颠倒"）
3. **判据表**（哪几节写不出来 = 没读懂）
4. **三条不要做**

正文里**故意不写**：每节的详细格式、字段表、脚本的用法细节。

**≤500 行**的真实含义是：正文该是**目录 + 规则**，不是手册。手册在 `references/`。

**判据**：2 分钟内能读完。读不完，说明你把层 3 的东西写进层 2 了。

---

## 第 4 步：把细节下沉到 `references/`（层 3）—— 按**使用频率**切，不按主题切

**要决定什么**：切几份。

我的切法只用一个标准 —— **多久读一次**：

| 文件 | 频率 | 为什么单独 |
|---|---|---|
| `note-template.md`（125 行） | 每篇一次 | 必做 |
| `index-template.md`（95 行） | 每批一次 | 半必做 |
| `extra-deliverables.md`（62 行） | 很少 | 按需 —— 和"必做"挤在一份里，会让只做笔记的人白读 100 行 |

**按主题切是错的**（比如"格式"一份、"内容"一份）：因为成本模型是按**读它的次数**算的。

模板里每一节必须写四样：**写什么 / 多长 / 判据 / 反例**。

> 反例是"合格的模板"和"一张清单"的分界。比如 §1 一句话结论的反例是
> "本文提出了一套评测环境并在多个模型上做了实验"——它满足了"一句话"，但等于没说。
> 没有反例，模板就只是限制字数。

**判据**：模板里每一条，你都能回答"不这么写会怎样"。答不出的那条删掉。

---

## 第 5 步：把确定性劳动变成脚本

**要决定什么**：哪些事该从"散文指令"变成"可以被执行的程序"。

判断标准很清楚：**有唯一正确答案的 → 脚本；需要判断的 → 留给人**。

| 变成脚本 | 留在正文 |
|---|---|
| 解析 JSONL、统计页码锚点数、检查节顺序、抓绝对路径 | "这条批判够不够狠"、"这个方法骨架有没有讲清" |

为什么值得：解析这类活**每次做都可能漏一个字段**（我自己就漏过 `usage_total` 取错字段）。
写成脚本后，207 / 333 行的实现**永不进入上下文**，只被调用。

脚本的两条硬要求：能独立跑（`python x.py <路径>`）、能输出 `--json` 给别的脚本消费。

---

## 第 6 步：写校验器 + **自检**（这一步决定它是"规范"还是"愿望"）

**要决定什么**：怎么证明"写对了"。

我的 `check_note.py` 查 9 条：元信息表 / 五段速记五行 / 八个角色的节顺序 / **页码锚点 ≥20** /
表图引用 ≥1 / 批判 ≥150 字 / 对接必须落到 `.py` 或 `::` / 术语表 ≥4 条 / 不许绝对路径。

**但校验器本身也必须被检验。** 所以它有 `--self-test`：造一个合法样本，再**逐个改坏 7 次**
（删术语表 / 去页码 / 批判压成一句 / 加绝对路径 / 删作者行 / 删局限段 / 对接写成空话），
确认每一个都会被报、且合法样本不被误报。

**自检第一次跑就抓出了我自己的 bug**：术语表行数阈值写成 6，合法样本被误报成"术语不足"。
一个只会点头的校验器，跑一万次也只给你"全部通过"。

---

## 第 7 步：校准 —— 拿你真做出来的东西当标准答案

**要决定什么**：规则是严了还是松了。

拿已有的 4 篇真笔记 + INDEX 跑校验器：

| 结果 | 说明 |
|---|---|
| 真笔记**通过** | 规则与你的实际做法一致 ✅ |
| 真笔记**不通过** | **规则错了**，不是笔记错了 —— 回去改规则 |
| 什么都能通过 | 规则太松，等于没查 |

实测 5/5 通过。这一步是"看起来合格"和"真的合格"的分界线。

---

## 第 8 步：触发测试 —— 新上下文，**不提名字**

**要决定什么**：`description` 到底行不行。

方法：开一个**新上下文的 subagent**，只描述任务（"把这篇论文搞明白、以后能在组会讲，
先别写，说你要产出几份文件、什么格式"），**一个字不提 skill 名字**。

看什么：**内容指纹** —— 答案里有没有"只有加载后才可能知道"的东西。实测它给出了：

- 四份产出的分档（L1 笔记 / INDEX / 自测 / 发言稿）
- 自测的 11 节结构
- 引用了模板里的硬要求（"这张表最弱的地方"）
- **并且真的去跑了 `check_note.py`，报出退出码 0**

最后一条是硬证据：它不可能凭空知道脚本名和退出码。

> 触发测试**必须在新的上下文里做**。在你自己对话里测是无效的 —— 你已经知道这个 skill 存在了。

---

## 反模式清单（七条，都是会真实发生的）

1. **`description` 写成"这个 skill 是关于 X 的"** → 能被发现，永不触发。
2. **把 500 行手册塞进正文** → 每次加载都为 90% 用不上的内容付费。
3. **模板只写"要写什么"，不写"不这么写会怎样"** → 它只是字数限制。
4. **校验器只会点头** → 和没有校验器一样，而且更危险（让你以为查过了）。
5. **不校准** → 规则比真做法严，于是你每次都要绕过自己的规范。
6. **在同一个上下文里做触发测试** → 100% 通过，零信息。
7. **把判断写成脚本**（或反过来把确定性解析写成散文）→ 前者僵硬，后者每次都不一样。

---

## 这个 skill 现在还差什么（不假装齐了）

1. **触发率还是 N=1**：只测了一次、一种措辞。要说"3/5 会触发"，得跑多措辞 × 多轮。
2. **硬信号还没落地**：会话轨迹是多帧 zstd，`zstdDecompressSync` 只解第一帧，读不出来。
   所以"它到底有没有调 `skill` 工具"目前靠内容指纹，不是靠日志。
3. **没被真用过一次**。一个 skill 只有在被真用、并因此改过一次之后，才知道哪条判据是废话。

## 附：这个 skill 的文件与成本

| 层 | 文件 | 行 | 何时进上下文 |
|---|---|---:|---|
| ① 常驻 | （catalog 里的 name + description） | —— | 每次会话，约 150 字 |
| ② 加载后 | `SKILL.md` | 56 | 判定相关时 |
| ③ 按需 | `references/note-template.md` | 125 | 每篇 |
| ③ 按需 | `references/index-template.md` | 95 | 每批 |
| ③ 按需 | `references/extra-deliverables.md` | 62 | 很少 |
| ③ 执行 | `scripts/check_note.py` | 333 | 从不被读，只被调用 |

> 合计 671 行，**常驻的只有那 150 字**。这就是"skill 能携带的上下文几乎无上限"的实际形状。
